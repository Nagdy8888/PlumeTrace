# PlumeTrace — AI Methane Leak Hunter for a Gas Compressor Station

Design document · 2026-11-12 · Status: draft for review (revised after design review, 2026-11-12)

---

## 1. Intent and the why

**What it is.** PlumeTrace is a web application that watches a gas compressor station in an
interactive 3D view. When methane shows up where it should not, a team of AI agents works out
whether it is a real leak, finds the leaking component, estimates how much is escaping (kg/h),
checks what the regulations require, and drafts the repair work order and emissions report.
A human operator approves every action.

**Why this problem.** Methane is a top industry pain right now, and it is getting more expensive:

- The **EU Methane Regulation (EU) 2024/1787** requires leak detection and repair (LDAR) surveys,
  strict repair deadlines, and limits on venting and flaring. It also applies to gas imported into the EU.
- **OGMP 2.0** (the UNEP Oil & Gas Methane Partnership) pushes operators to move from estimated
  emission factors (Level 1–3) to measurement-based, source-level reporting (Level 4) reconciled
  with site-level measurements (Level 5).
- Satellites (e.g. Carbon Mapper, GHGSat, Sentinel-5P/TROPOMI) now spot large leaks publicly, so a
  leak the operator missed can become public before the operator knows about it.

Operators already have the raw data (fixed gas detectors, weather stations, flare meters, OGI
camera surveys, process tags). What they lack is a fast way to join it all up into one answer:
*what is leaking, how much, what must I do, and by when.* That joining-up is what PlumeTrace's
agents do.

**Why it exists (for the owner).** It is a LinkedIn portfolio project. It must look and behave
like a real industrial product, show genuine process engineering, and show credible agentic AI.
The owner is comfortable with both process engineering and full-stack/AI code, so the
engineering content must stand up to scrutiny from other engineers.

## 2. Goals, non-goals, anti-goals

### Goals
1. A striking, interactive **3D model of a compressor station** where gas leaks are visible as
   plumes drifting with the wind.
2. **Real engineering behind the numbers**: a Gaussian plume dispersion model, a source
   inversion (localisation + quantification) with uncertainty, a flare combustion model, and a
   component inventory with published emission factors.
3. **A multi-agent AI pipeline** (OpenAI) that uses those engineering tools, explains its
   reasoning step by step, and drafts outputs. The AI never makes up a number; every number
   comes from a tool.
4. **Human-in-the-loop**: the operator approves or rejects each work order and report.
5. **Six realistic scenarios** including false alarms the AI must correctly dismiss.
6. **A public live link** (replay mode, zero AI cost) plus a **recorded video** and a public GitHub repo.
7. **A published accuracy figure**: localisation and quantification accuracy measured over many
   randomised synthetic leaks. This is the credibility anchor for engineers.

### Non-goals
- Not connected to any real plant, SCADA, historian or CMMS.
- No user accounts, multi-tenancy or authentication.
- No mobile app or mobile 3D: phones get a mobile page with the demo video (section 9).
- Not a certified regulatory reporting tool.
- No CFD. Gaussian plume physics is the deliberate fidelity level.

### Anti-goals (would make it a failure even if it works)
- **Looks like a toy demo**: random-number sensors, generic chatbot UI, lorem-ipsum tags.
- **The AI invents engineering numbers** or regulatory facts not backed by a tool or a cited source.
- **The AI acts on its own** (closes valves, files reports) without operator approval.
- **Pretends to be a real site or company**: no real operator names, logos or real plant data presented as genuine.
- **A public site that can run up an AI bill** or leak an API key.
- **Choppy 3D** on an average laptop (target: 60 fps on integrated graphics at 1080p).

## 4. The facility (fictional: "Station KS-07")

A fictional mid-size onshore compressor station on a gas export pipeline **outside the EU that
supplies gas to the EU**. Layout roughly 200 m × 150 m. Fictional site placed in a real region so
real weather data can be pulled: a flat desert/steppe region in Central Asia, the Middle East or
North Africa where public satellite plume data is dense (the builder picks the region and exact
coordinates, checking Carbon Mapper coverage first).

**Compliance framing that follows from the location:** the EU Methane Regulation's LDAR, repair
and venting articles do not bind a non-EU site directly; the EU importer does, through the
regulation's import requirements and "equivalence" provisions. So PlumeTrace frames compliance as:
- **OGMP 2.0** reporting (the operator's own commitment), and
- an **operator LDAR policy modelled on EU 2024/1787** (the repair deadlines, venting limits and
  super-emitter handling), presented as "EU-import readiness" for the gas buyer.
The UI and reports say this plainly; they never claim the EU articles apply to the site directly.

### Equipment (each a 3D object with a tag)
| Area | Equipment | Example tags | Typical methane sources |
|---|---|---|---|
| Inlet | Pig receiver, inlet filter-separator | V-100, PIG-101 | Pig door seals, flanges, PSV |
| Compression | 3 × reciprocating compressor units, each with suction scrubber, compressor, gas-engine driver, aftercooler (fin-fan); **packing vents of all three units routed to a common vent header and vent stack VS-250** | K-201/202/203, V-211, E-231, VS-250 | **Rod packing vents (via VS-250)**, engine methane slip, blowdown valve passing, flanges |
| Dehydration | TEG contactor + regenerator (still column) | T-301, R-302 | Still column vent |
| Storage | 2 × condensate tanks + vapour recovery unit (VRU) | TK-401/402, VRU-410 | **Thief hatch** open, VRU downtime |
| Utilities | Fuel gas skid, instrument gas, pneumatic controllers | FG-501, PCV-xxx | **High-bleed / malfunctioning pneumatics** |
| Safety | Flare stack with pilot + knock-out drum, blowdown system | FL-601, V-602 | **Unlit flare**, low combustion efficiency |
| Outlet | Discharge header, meter run, pig launcher | FT-701, PIG-702 | Flanges, connectors |
| Buildings | Control room, MCC, compressor shelters | — | — |

Tag style follows ISA-5.1 conventions. Each equipment item also has a **component inventory**
(counts of valves, flanges, connectors, open-ended lines, PSVs, pneumatics) used by the
emission-factor model.

**Facility spec authoring (avoid hand-placing thousands of parts):** `ks07.yaml` describes
equipment (tag, type, position, size, nozzles) and piping routes (waypoints, line size, service).
Component **counts** come from published per-equipment-class component-count tables (cited);
flanges/valves are **placed procedurally** along piping routes and at nozzles by a generator,
which also emits the candidate-source list for the inversion. Nothing is hand-placed except
equipment and routes.

**Gas composition:** a fixed pipeline-quality gas composition (mole fractions, e.g. CH₄ ≈ 0.90–0.95,
C₂H₆, C₃H₈, CO₂, N₂ — builder picks a cited typical composition) used for density, real-gas Z
factor, and converting gas volumes (scf/h, Sm³/h) to **kg CH₄/h**.

### Instruments (what the simulator produces)
- **Fixed continuous methane sensors**: ~8 point sensors around process areas and the fence line (ppm, 1 s–10 s data).
- **Met mast**: wind speed, wind direction, temperature, solar radiation/cloud cover → atmospheric stability class.
- **Flare**: flow meter and pilot thermocouple.
- **Vent header flow meter FT-250** on the common packing-vent header (total, not per unit) and
  **packing-case temperature** TT-201P/202P/203P per compressor (a leaking packing runs hot).
  Per-unit attribution is therefore an inference, not a direct reading.
- **Tank pressure** and VRU run status.
- **Process tags**: suction/discharge pressure and temperature, throughput, fuel gas flow — enough for a station mass balance.
- **OGI camera survey results**: periodic (e.g. quarterly) simulated surveys listing detected components.
- **Satellite pass**: occasional simulated detection with a detection threshold (only big leaks are seen), alongside real public plume data for regional context.
- **Quarterly aerial site survey** (simulated drone/aircraft campaign): a site-level total
  emission rate with its own uncertainty. This is the "top-down" measurement used for the OGMP
  2.0 Level 5 reconciliation (my call).
- **Maintenance / permit-to-work log**: planned blowdowns and maintenance, so the AI can tell planned venting from leaks.

## 5. Engineering core (deterministic, tested, no AI)

All engineering lives in a plain Python package the agents call as tools. It must be correct
on its own and unit-tested against known values.

0. **Truth model vs inversion model (no inverse crime anywhere).** The **simulator and the
   benchmark share one "truth model"** that generates sensor data with *different* physics from
   the inversion: a different dispersion-coefficient set, wind meander / sub-hourly direction
   fluctuation, simple building/equipment wake effects, and sensor response/noise. The inversion
   only ever uses the plain Gaussian model. The demo scenarios are therefore as hard as the
   benchmark, and no scenario is "solved by construction".
1. **Gaussian plume forward model.** Ground-level concentration at each sensor from a point
   source at height *h*, rate *Q*, wind speed *u*, direction θ, with ground reflection.
   Background methane ~1.9–2.0 ppm plus sensor noise.
   - **Near-field validity:** sensors sit 10–150 m from sources, below the ~100 m lower bound of
     classic Pasquill–Gifford fits. Use a dispersion-coefficient set valid at short range (builder
     picks and cites, e.g. short-range fits used in near-field/fence-line work) and document the
     validity range in `ENGINEERING.md`.
   - **Averaging time:** the model predicts a mean concentration over an averaging period;
     sensor data (1–10 s) is averaged over a defined window (e.g. 10 min) before inversion, and
     the window is a documented parameter.
   - **Calm and very stable conditions** (wind < ~1 m/s, or class F nights with low wind) are
     outside the model: the inversion returns `inconclusive` with the reason, by design.
1a. **Stability class from weather.** Pasquill class derived from wind speed, solar radiation
   (day) and cloud cover (night) using the Turner method; sub-hourly wind fluctuation synthesised
   from hourly Open-Meteo data in the truth model only.
1b. **Event detection (code, not AI).** Rolling per-sensor baseline + a stated change-detection
   method (e.g. CUSUM on the averaged signal), minimum persistence, and wind-consistency check;
   a false-alarm-rate target measured on no-leak simulations.
2. **Source inversion (localisation + quantification).** Given sensor readings over a time
   window with changing wind, compute a posterior probability over the **candidate sources
   from the component inventory** and over the emission rate. Approach (my call): Bayesian
   grid/MCMC over candidate source × rate, with a likelihood from the forward model and sensor
   noise. Output: ranked candidates with probabilities and a rate estimate with a 90% interval.
2a. **Evidence fusion (coded, not AI).** Combines the inversion posterior with process evidence
   into one posterior over candidates: e.g. vent header flow FT-250 rising, packing-case
   temperatures TT-20xP (one unit hotter than its siblings), flare pilot status, tank pressure /
   VRU status, permit log. Implemented as a documented Bayesian update with explicit likelihoods
   per evidence type, unit-tested. The headline "K-202 rod packing 87%" comes from **this tool**,
   never from the LLM's judgement.
3. **Flare model.** Combustion/destruction efficiency as a function of pilot status and
   conditions; methane slip in kg/h. An unlit flare = 100% of flared gas vented.
3a. **Gas properties.** Gas composition → molar mass, density, real-gas Z factor (cited
   correlation), and conversions from gas volume flow to kg CH₄/h.
3b. **Blowdown vented mass (S4).** Isolated volume (vessels + piping from the spec) × initial
   and final pressure/temperature → vented gas mass via real-gas Z → kg CH₄.
4. **Emission-factor inventory (OGMP Level 1–3 style).** Component counts × published emission
   factors (builder picks and cites the exact source) → a "bottom-up" site estimate. Two factor
   types, used for different jobs: **average factors** for the site inventory and **"leaker"
   (leak/no-leak) factors** for a component found leaking by OGI without a measurement (S6).
4a. **Methane intensity.** CH₄ emitted ÷ gas throughput, on one named, cited basis (volume or
   energy), stated next to the KPI.
5. **Site mass balance.** Inlet − outlet − fuel − flare. Flags only large unaccounted losses,
   with meter uncertainty shown honestly.
6. **OGMP 2.0 Level 5 reconciliation.** Compare the bottom-up source-level inventory (Level 4)
   with two top-down site-level estimates and show the gap with uncertainty:
   - the **quarterly aerial survey** (primary top-down figure), and
   - a **continuous fence-line inversion** of total site emissions from the fixed sensors (between surveys).
   The mass balance is shown only as a coarse cross-check. The OGMP badge claims Level 5 only
   when an aerial survey falls within the reporting period; otherwise it shows Level 4.
7. **Units and conversions.** kg/h, t/yr, scf/h, CO₂-equivalent (GWP-100 and GWP-20, with the
   source of the GWP values cited).

### Validation (published in the README)
- Plume model unit tests against textbook worked examples.
- **Inversion benchmark with model mismatch**: N ≥ 200 randomised synthetic leaks. To avoid the
   "inverse crime" (testing with the same model used to invert), the test leaks are generated with
   **different physics** from the inversion:
   - a different dispersion-coefficient set than the inversion uses,
   - wind meander / short-term direction fluctuation,
   - simple building/equipment wake effects near shelters,
   - some sources placed **off the candidate list** (e.g. between components),
   - random rate, weather, sensor noise and occasional sensor faults.
   Report: top-1 and top-3 localisation accuracy, rate error (median and 90th percentile), the
   **"inconclusive" rate**, and the false-call rate on no-leak cases. Results are broken down by
   stability class and leak size.
   The numbers are published honestly in the README. If top-1 accuracy is weak, the first fix is
   allowed: improve the sensor layout and the method, then re-run once. Whatever comes out after
   that is published as it is. This is the credibility anchor.

## 6. The AI agents (OpenAI)

The pipeline is a **LangGraph `StateGraph`** with mostly fixed edges, each specialist agent a
node (or a small subgraph) with its own tools wrapping the engineering core. Code-defined edges
(not an LLM) decide the order, so runs are reproducible and recordable for replay. Conditional
edges exist only where the design needs a branch:
- after **Triage**: real leak → Locate; sensor fault → instrument ticket draft; planned venting → log-only;
- after **Approval**: approve/edit → done; reject → redraft once → approval again; second reject → escalate.

```
START → detect_event → triage ─┬─ leak ──→ locate_quantify → compliance → draft_outputs → approval ─┬─ approve/edit → finalize → END
                               ├─ sensor_fault ──────────────────────────→ draft_outputs ↗         ├─ reject (1st) → redraft → approval
                               └─ planned_venting → log_vented_volume → finalize                    └─ reject (2nd) → escalate → END
```

LangGraph specifics (checked against current LangGraph docs, 2026-11):
- **Human approval uses `interrupt()`** in a dedicated `approval` node, resumed with
  `Command(resume=<decision>)` on the same `thread_id`. This needs a **checkpointer**:
  LangGraph's `PostgresSaver` on the local Supabase Postgres (connection string injected by the
  backend); in-memory in tests.
- **On resume, the interrupted node re-runs from its start.** So the `approval` node must do
  nothing before `interrupt()` except build the payload: no LLM calls, no writes, no side effects.
- One graph run = one `thread_id` = one PlumeTrace run id.
- Graph state is a typed schema (TypedDict or Pydantic) holding the event, evidence, tool results,
  drafts, decisions and revision count.

**LangSmith:** tracing is turned on with environment variables (`LANGSMITH_TRACING`,
`LANGSMITH_API_KEY`, plus the workspace's destination setting — current docs show both the
older project-name variable and newer agent-addressing variables; the builder checks which one the
account uses). Each run is tagged with scenario id, run id and branch (approve / reject path).
LangSmith is used for:
1. **Debugging** every node, tool call and LLM call — every paid run is traced (a paid run is
   refused when tracing is off).
2. **Evaluations**: scenarios S1–S6 (and benchmark variants) become a LangSmith dataset, with
   evaluators for: correct triage outcome, correct top source, rate within the tool's interval,
   correct rule cited, and "every number in the draft appears in a tool output".
LangSmith is **not** the public replay source (it needs an account and API key). Public replay uses
PlumeTrace's own trace files, exported from the graph's event stream.

| # | Agent | Job | Tools (examples) |
|---|---|---|---|
| 0 | *Detection* (code, not AI) | Raise an "event" when sensors exceed a dynamic threshold vs background, or a satellite/OGI hit arrives | — |
| 1 | **Triage agent** | Real leak, sensor fault, or planned/permitted venting? | `get_sensor_history`, `get_weather`, `get_permit_log`, `get_process_tags`, `check_sensor_health` |
| 2 | **Locate & quantify agent** | Run the inversion, gather process evidence, run the coded evidence fusion; decide whether to accept the result or ask for an OGI survey | `run_plume_inversion`, `get_component_inventory`, `get_vent_header_flow`, `get_packing_temperatures`, `get_flare_status`, `get_tank_status`, `get_ogi_results`, `fuse_evidence`, `request_ogi_survey` |
| 3 | **Compliance agent** | Classify the event (leak to repair vs venting vs flaring), set repair deadlines under the operator LDAR policy modelled on EU 2024/1787, flag super-emitter and OGMP 2.0 reporting duties | `lookup_regulation_rule` (a curated, cited rules table — not the LLM's memory), `compute_co2e` |
| 4 | **Work order & report agent** | Draft the CMMS-style work order, the shift-log entry and the OGMP 2.0 report line | `create_draft_work_order`, `create_draft_report` |
| — | **Operator (human)** | Approve, edit or reject each draft | UI approval |

### What the AI decides (the answer to "why an LLM at all?")
The **graph order is fixed**, but **inside each node the agent chooses its own tools** in a
bounded ReAct loop (max 6 tool calls per node, then it must conclude or return `inconclusive`).
The LLM's real jobs are the ones rules handle badly:
- reading **messy free text** — permit-to-work entries, OGI survey notes, shift notes, operator
  rejection reasons — and relating it to the sensor event (e.g. "gauging at TK-402 at 09:10");
- **choosing which evidence to fetch** for this event, and when evidence is weak, deciding to
  request an OGI survey instead of forcing an answer;
- weighing conflicting qualitative evidence in **triage** (leak vs sensor fault vs planned venting);
- **drafting** work orders, shift-log entries and report lines that an engineer would sign.
Quantitative judgement (where, how much, which deadline) stays in coded tools (`fuse_evidence`,
the inversion, the rules table).

**Measured value, not claimed:** a **rule-based baseline triage** (thresholds + keyword matching on
the permit log) runs on the same scenario variants; the README reports AI vs baseline triage
accuracy, plus cost and latency per run.

### Number provenance (makes rule "numbers come from tools" checkable)
Every numeric field in an agent output schema is a `SourcedNumber`: value, unit, and
`source_tool_call_id` pointing at the tool call that produced it. A **guard in code** (not only an
evaluation) rejects an output whose number does not match its source tool output (after unit
conversion/rounding rules). Free text may only repeat sourced numbers. The UI shows the source on hover.

### Budgets for live mode
- Target per run: **≤ 90 s** wall time and **≤ $0.05** model cost; hard stop at 2× budget
  ($0.10 / 180 s) → run marked `aborted_budget`. (Owner decision 2026-11-13; was $0.30.)
- **Total spend cap $4.00** for all paid calls of the project (smoke, live, evaluation, trace
  recording), enforced in code from the `llm_calls` ledger (owner decision 2026-11-13).
- Model (owner decision 2026-11-13): **`gpt-6-luna`** for every node through the Responses API;
  reasoning effort `low` for triage on clear cases and drafting, `medium` where reasoning quality
  matters (ambiguous triage, locate & quantify).
- `max_tokens`, timeouts, one retry, `recursion_limit`; tokens and cost written to `runs`.
- **Simulation time pauses while the agents work** (the operator sees "agents investigating");
  it resumes after the run reaches approval or finishes.

### Agent evaluation (statistically meaningful)
- **Scenario families:** a generator produces ~20 randomised variants of each scenario (weather,
  leak rate, timing, distractor log entries, sensor noise) → ~120 cases (MVP: S1/S4/S5 families
  ≈ 60 cases).
- Each case runs **3 times** (LLM non-determinism); report mean and spread. Under the $4 spend
  cap the run is sized to what is affordable (fewer repeats or a per-family subset), and the
  report states the reduction.
- Metrics: triage accuracy, top-source accuracy (vs fusion truth), rate-within-interval,
  correct rule cited, numbers-provenance pass rate (must be 100%), inconclusive rate, cost and
  latency per run — and the rule-based baseline on the same cases.
- Lives in `app/agents/evals/`, results in LangSmith experiments and `docs/evidence/`.

Rules for every agent:
- Every number in an agent's output must come from a tool result (`SourcedNumber`, enforced by the guard); the UI shows which tool produced it.
- Regulatory statements come only from the curated rules table, each rule with a citation
  (article number + link). The table's contents must be checked against the regulation text by the builder.
- Agents output **structured JSON** (schema-validated), plus a short plain-English rationale shown in the UI.
- An agent can say "inconclusive — request OGI survey of area X" instead of forcing an answer.
- The curated rules table is the source of truth. If checking it against the regulation text
  contradicts a scenario's intended "right answer" (e.g. a rod packing vent is classed as venting,
  not a leak to repair), **the regulation text wins** and the scenario's expected answer is updated.

### Operator approval and one redraft
- **One approval per run, as a bundle**: the work order, shift-log entry and report line are
  reviewed together in one dialog (they describe one event). A rejection reason applies to the
  bundle; the redraft agent revises only the drafts the reason concerns.
- **Approve** → the bundle is marked approved and logged (work order "issued", report "filed" — both simulated).
- **Edit** → text fields are editable; **numeric fields are locked** to their sourced values. If
  the operator must change a number, it is entered as an explicit **"operator override"** with a
  reason, shown as such in the record and excluded from the numbers-provenance check.
- **One event at a time:** while a run is awaiting approval, new detection events are queued
  (shown in the alarm list as "queued") and processed after the current run finishes.
- **Reject with a reason** → the drafting agent revises **once**, using the reason. The operator then
  approves, edits or rejects the revision. A second rejection is final and is logged as
  "escalated to engineer" (no further AI drafts).

### Recording and replay
Every live run is recorded as a **trace file**: the events, each agent's messages, each tool call
with inputs/outputs, timings, and the drafts. The public site replays traces with original timing,
so it looks live but costs nothing. Traces are versioned with the scenario that produced them.

Traces have **branches** at each approval point. For every scenario two paths are pre-recorded:
**approve**, and **reject-with-a-preset-reason → redraft**. In replay, the reject button offers that
preset reason, so both buttons lead somewhere real. Free-text reasons and edits only work in local live mode.

## 7. Scenarios (the demo story set)

| # | MVP? | Scenario | What happens | What the AI must get right |
|---|---|---|---|---|
| S1 | **MVP (hero)** | **Rod packing failure, K-202** | ~10–20 kg/h out of common vent stack VS-250; downwind sensors rise as the wind shifts; FT-250 header flow up; TT-202P runs hotter than TT-201P/203P | Inversion locates VS-250; `fuse_evidence` attributes it to K-202 packing with a probability; quantifies with uncertainty; classifies per the rules table; drafts the work order with the policy deadline |
| S2 | stretch | **Tank thief hatch left open** after gauging | Intermittent ~30–50 kg/h from TK-402 | Ties it to the gauging entry in the log, links to the VRU status |
| S3 | stretch | **Unlit flare** (pilot out) | >100 kg/h, satellite also detects it | Flags a super-emitter event, top urgency, drafts the notification the operator policy requires (and warns that a public satellite detection is likely) |
| S4 | **MVP** | **Planned blowdown** (false alarm) | Big short spike during a permitted maintenance blowdown | Checks the permit log and correctly dismisses it as planned venting, while still logging the vented mass from the blowdown tool |
| S5 | **MVP** | **Sensor drift** (false alarm) | One sensor slowly reads high, no others agree, wind-inconsistent | Diagnoses a sensor fault, raises an instrument maintenance ticket, not a leak |
| S6 | stretch | **Small flange leak** below fixed-sensor detection | Found only in the quarterly OGI survey | Logs it from OGI evidence, estimates the rate with leaker factors, sets a repair deadline |

Each scenario is a seeded, repeatable simulation script (start time, weather source, leak
source/rate/timing, sensor faults, log entries).

The real satellite data is clearly labelled as real regional context; the station itself and its
leaks are clearly labelled as simulated. Nothing simulated is presented as real.

## 9. Frontend and 3D

**Look:** a dark, modern control-room UI (my call). Dense with real-looking data but uncluttered. No stock "AI sparkle" visuals.

**Time model.** Each scenario is a fixed span of simulated time (e.g. 2–6 h) on a simulation
clock with playback speeds (1×, 10×, 60×, 300×), pause and scrub. The hero replay is cut so the
story plays in ~90 s at its default speed. Agent runs happen at a point in sim time; **sim time
pauses while agents work** and resumes after approval (live and replay behave the same).

**First 10 seconds (desktop).** The public site opens straight into **autoplay of S1** with short
captions at key moments ("Methane rising at fence sensor AT-104", "Agents investigating",
"K-202 rod packing — 87%", "Awaiting operator approval"); any interaction hands control to the visitor.

**Mobile.** Phones (small viewport or touch-only) get a **mobile page**: the demo video, a short
summary of what PlumeTrace does, and "open on a desktop for the live replay". No 3D on phones.

**Layout (desktop):**
- **Centre — 3D station.** Spec-generated, Blender-baked equipment (glTF) with PBR materials, pipe racks, grating, shelters,
  lights. Plumes rendered as wind-driven particle volumes whose density matches the plume model.
  Optional ground concentration heat-map. Wind arrow/windsock. Day/night lighting from time of day.
  Click any equipment → tag card (live values, component inventory, recent events).
  When the AI locates a source, the camera flies to it and the candidate components glow by probability.
- **Left — Events & alarms.** ISA-18.2-style event list with priority, time, tag, state.
- **Right — Agent panel.** A step-by-step timeline: which agent is working, its reasoning summary,
  each tool call ("Running plume inversion… 3 candidates, K-202 packing 87%"), and the drafts.
- **Bottom — Trends.** Sensor ppm, wind, vent header flow FT-250 and packing temperatures, flare flow — with the event window highlighted.
- **Top bar — KPIs.** Site emission rate (kg/h), methane intensity, open leaks + days to deadline, OGMP level badge, scenario selector, replay controls.
- **Approval dialog** for work orders and reports (approve / edit / reject, with a reason).
- **Reports** exportable as PDF.

**Stack (my call):** React + TypeScript + Vite, React Three Fiber + drei + postprocessing,
Zustand for state, Tailwind for styling, a charting library for trends. Live mode streams over
WebSocket; replay mode reads trace and scenario files.

**Performance:** instanced meshes for repeated items (valves, grating, pipe supports), GPU particles
for plumes, capped pixel ratio, quality setting. Target 60 fps on integrated graphics at 1080p.

## 10. Architecture and deployment

```
 ┌──────────────────────────── LOCAL (full, live mode) ────────────────────────────┐
 │ app/frontend (Vite dev) ──REST/WS──▶ app/backend  FastAPI  (plumetrace.api)     │
 │                                        │   simulator · engineering · rules        │
 │                                        │   agent_tools (implements ToolProvider)  │
 │                                        ▼                                          │
 │                         app/agents  LangGraph graph (plumetrace_agents)           │
 │                                        │  OpenAI models ──▶ LangSmith (dev traces │
 │                                        │                     + evaluations)       │
 │                                        ▼                                          │
 │   app/supabase  local Supabase Postgres: plumetrace.* tables + LangGraph          │
 │                 checkpoint tables (PostgresSaver)                                 │
 │                                        │                                          │
 │                     scripts/record_traces ──▶ app/replay/ (scenarios + traces)    │
 └──────────────────────────────────────────────────────────────────────────────────┘
 ┌──────────────────────────── PUBLIC (Vercel, replay) ────────────────────────────┐
 │ Static build of app/frontend + app/replay. No backend, no database, no keys,     │
 │ no AI cost.                                                                       │
 └──────────────────────────────────────────────────────────────────────────────────┘
```

- **Three apps under `app/`:** `backend` (FastAPI + engineering + simulator, package
  `plumetrace`), `agents` (LangGraph, package `plumetrace_agents`), `frontend` (React/Vite).
  The two Python apps form one **uv workspace** (`app/pyproject.toml`) sharing one virtual env.
  **Dependency direction is backend → agents only:** the agents package never imports the
  backend; the backend injects the tools (`agent_tools/` implements the agents' `ToolProvider`
  protocol), the OpenAI chat model and the checkpointer into `build_graph(...)`. This keeps the
  graph testable with fakes and avoids a circular dependency. The graph runs inside the backend
  process (no separate agent server).
- **Local mode:** `npx supabase start` (Docker) + backend + frontend; scenarios run live; agents call
  OpenAI; runs, steps, drafts and decisions are stored in Supabase; runs can be recorded to
  `app/replay/`.
- **Replay data budget:** ≤ 5 MB compressed per scenario branch. Sensor series downsampled to the
  averaging window (raw 1 s data is not shipped), plume fields stored per key frame and
  interpolated, files split per scenario and loaded on demand (gzip/brotli via Vercel).
- **Public mode on Vercel:** static build only. Scenario sensor data and agent traces are
  precomputed files. Visitors pick scenarios, scrub time, orbit the 3D scene, click equipment and
  approve/reject drafts — all in replay. A "Replay of a recorded AI run" label keeps it honest.
  `app/frontend/vercel.json` sets security headers; the Vercel project holds no secrets.
- **Secrets:** the OpenAI and LangSmith keys and the Supabase connection string live only in a
  local `.env` (committed `.env.example` holds names only), never in the frontend, Vercel, the
  repo or exported trace files.

### 10.1 Database (local Supabase Postgres)

Supabase runs locally via the Supabase CLI (Docker). The backend connects with the direct Postgres
connection string (psycopg 3 with a connection pool, plain parameterised SQL in `plumetrace.db`;
my call: no ORM). The frontend never connects to Supabase. Schema `plumetrace`, created only by
migrations in `app/supabase/migrations/`; RLS enabled on every table with no `anon`/`authenticated`
policies (only the backend, as the database owner, reads and writes).

| Table | Holds |
|---|---|
| `scenarios` | Scenario catalogue (id, title, seed, version) — seeded |
| `runs` | One row per live run: `run_id` (= LangGraph `thread_id`), scenario, branch, status, timings, model ids, token/cost totals, LangSmith run URL |
| `llm_calls` | Every billed OpenAI call: run, node, role, model, effort, tokens (incl. cached and reasoning), cost, latency — the spend ledger |
| `app_logs` | Backend log records (redacted), with run id where known |
| `eval_results` | Evaluation scores per case and repetition |
| `events` | Detection events raised during a run (time, trigger, sensors, severity) |
| `sensor_readings` | Time series per run and sensor (time, tag, value, unit) — used for trends and trace export |
| `agent_steps` | Ordered agent timeline per run: node, tool calls (inputs/outputs), summaries, timings |
| `drafts` | Work order / shift log / OGMP report drafts with revision number |
| `decisions` | Operator decisions (approve / edit / reject + reason), bound to run, interrupt id and draft revision — the authoritative approval record |
| `work_orders`, `reports` | Final approved outputs (status "issued"/"filed" — simulated) |

LangGraph's `PostgresSaver` creates its own checkpoint tables in the same database at backend
start-up (`.setup()`). Checkpoints hold graph state for pause/resume; they are not the approval
record. Each table and column is documented in `docs/reference/DATABASE.md`.

## 15. Build rules and skills for the AI coding agents that implement this

This project will be built by AI coding agents (Claude Code sessions and subagents) working from
the implementation plan. These rules stop them from going wrong. They now live in the
project-root **`CLAUDE.md`** (the authoritative copy, loaded by every agent session), and the
project skills live in **`.claude/skills/`**: `engineering-core`, `langgraph`, `langsmith-trace`,
`fastapi`, `frontend-design`, `frontend-structure`, `shadcn`, `impeccable`,
`project-documentation`, `verify-and-review`, `contribution-workflow`, `repo-structure` (binding
repo layout, "no god files" limits + `check_structure.py`), `frontend-3d` (R3F scene, procedural
equipment, plume rendering, 3D performance and testing), `security-checks` (commit/phase/release gates +
`secret_scan.py`). Python docstrings follow the Google style. The root `skills/` folder
holds the unadapted source copies and is ignored.

### 15.1 Hard rules
1. **Check current docs before writing library code.** Use the Context7 docs tool (or the
   official docs) before any code that uses LangGraph, LangChain, LangSmith, langchain-openai,
   FastAPI, Pydantic, React Three Fiber, drei or postprocessing. Never rely on memory for these
   APIs; they change often. Two examples already found: LangGraph's newer event-streaming API,
   and LangSmith's newer agent-addressing variables.
2. **Pin versions.** Exact versions in `pyproject.toml` / lock file and `package.json` / lockfile.
   Record the versions checked in the docs lookup in the plan task.
3. **Engineering core is pure and test-first.** No LLM, no I/O, no global state. Write the test
   first (TDD). SI units inside; unit suffixes in names (`rate_kg_h`, `u_m_s`, `conc_ppm`).
   Physics tests use cited textbook values; the citation goes in the test docstring.
4. **The LLM never produces an engineering number.** Every number in agent output must come
   from a tool result in the same run. A check enforces it (the "numbers-from-tools" evaluator
   in tests and in LangSmith).
5. **Structured outputs only.** Every agent node returns a Pydantic-validated model. Invalid
   output → retry once → fail the node visibly. Never silently fill defaults.
6. **LangGraph rules:**
   - `interrupt()` only in the dedicated `approval` node, with nothing before it but building the payload (the node re-runs on resume).
   - Always compile with a checkpointer; always pass `thread_id`; resume with `Command(resume=...)`.
   - Edges are code-defined; conditional edges only at triage and approval (section 6).
   - Each graph change needs a test that runs the graph with a **fake LLM** (no network) through every branch.
7. **LangSmith rules:** tracing on only through env vars; tag every run with scenario id, run id
   and branch; never put secrets or full sensor dumps in trace metadata; tests run with tracing **off**.
8. **Regulatory content only from the curated rules table**, each rule with article/section and
   link. Never write regulatory statements into prompts or UI copy from memory.
9. **Secrets:** `.env` is git-ignored; `.env.example` has names only. No key in the frontend,
   the static build or exported traces. A test scans the static build and traces for key patterns.
10. **Honest labelling:** the station is labelled simulated, real data is labelled real and
    attributed. No real operator names or logos.
11. **Verify before claiming done.** Run the tests, lint and type-check, and show the output.
    For UI tasks, open the page and check it. "Should work" is not done.
12. **3D performance budget:** 60 fps at 1080p on integrated graphics. Repeated parts use
    instancing. Every new scene feature is checked against the budget.
13. **Skill install gate:** any new skill or plugin (for example a LangGraph skill) goes through
    the SkillSpector security scan from the owner's global `CLAUDE.md` before install.
