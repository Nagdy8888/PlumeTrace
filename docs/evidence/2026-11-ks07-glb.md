# Phase 4 Task 7: the full-station `ks07.glb` (budgets, bake time, screenshots)

Date: 2026-11-16. Blender 4.5.16 LTS, glTF-Transform CLI 4.5.1, seed 20261113, Windows 11. The glb is
generated by `scripts/build_station.sh high` (the command that regenerates it; see
[STATION_MODEL.md](../reference/STATION_MODEL.md)). This file records what the commands printed.
The station is fictional and simulated; nothing here is a claim about visual fidelity, only
measurements and the screenshots listed below.

## Budgets (final run, `--texture-size 512`)

`scripts/build_station.sh high`, last lines of the real output:

```text
build_station: build\ks07_raw.glb bake=high bake_s=108.6 total_s=121.2
info: ks07_raw.glb (32.53 MB) -> ks07.glb (3.17 MB)
glb OK: 70 nodes, 3165648 bytes, 110484 triangles, 168 draw calls
51 textures, gpuSize sum = 71.4 MB decimal (68.1 MiB)
```

The last line is the sum of the `gpuSize` column of the TEXTURES table in `build/ks07_inspect.txt`
(a throwaway script outside the repo added the 51 rows; all 51 are 512 x 512).

| Budget | Limit | Result | Pass |
|---|---|---|---|
| file size | at most 15,000,000 bytes | 3,165,648 | yes |
| triangles | at most 1,500,000 | 110,484 | yes |
| draw calls (estimate: node-with-mesh x primitive) | at most 300 | 168 | yes |
| GPU texture memory (`gpuSize` sum) | at most 128 MB | 71.4 MB | yes |
| tags, anchors and the 7 separate nodes present | 0 missing | 0 missing (`check_glb.py`, no `--only`) | yes |

The draw-call figure is the generator's estimate. In the browser at the review camera `r3f-perf`
showed 260 `calls` and 139,136 triangles per frame; that count includes the sun's shadow pass (every
mesh is drawn twice), it is a single viewpoint, and the proper confirmation (`gl.info.render.calls`)
is Task 8. No limit was raised.

Where the numbers come from (raw glb JSON, before the optimiser): 168 node-primitive pairs and
110,484 triangles = equipment and separate nodes 107 pairs / 83,548 triangles (Task 6 counted
83,550 with the two-triangle spike ground), 15 piping routes 55 pairs / 19,180 triangles,
`SITE__ground` 4 pairs / 268 triangles, `SITE__racks` 1 / 684, `SITE__fence` 1 / 6,804. After
`optimize` the glb has 91 nodes: the 70 named ones plus 21 unnamed child nodes that carry the
meshes (each holds the mesh and its quantisation scale and translation; added by the meshopt step).

## The texture-size ruling (owner ruling C4, new step 0)

The plan command uses `--texture-size 1024`. That run (same Blender output, only the optimiser
flag differs) printed:

```text
info: ks07_raw.glb (32.55 MB) -> ks07.glb (5.54 MB)
glb OK: 70 nodes, 5544704 bytes, 110540 triangles, 168 draw calls
```

and its texture table summed to **163.6 MB** (22 textures at 1024 x 1024, 29 at 512 x 512), over the
128 MB budget. Per the owner ruling the first fix is `--texture-size 512`; it gave **71.4 MB** and
3,167,404 bytes in the first 512 run (3,165,648 after the fence fix below), so the later fixes (smaller AO for small footprints, 24 segments, asking the owner)
were not needed and the limits are unchanged. Side effect: the 1024-pixel AO images of the
compressors and the ground are downsized to 512 by the optimiser; `ao_resolution` still asks for 1024
there, so the bake time below includes work that the shipped glb does not keep.

Why 51 textures and so many 1024 ones before the cap: the Blender glTF exporter merges an item's AO
image (R channel, UV set 1) and the roughness map of a textured material (G channel, UV set 0) into
one image (`K-201_ao-concrete_floor_02_rough_1k`), and the occlusion and metallic-roughness slots
both point to it with their own `texCoord`.

## Check C5: separate nodes

`check_glb.py` without `--only` reported 0 missing nodes. The seven separate nodes
(`E-231__fan_1`, `E-231__fan_2`, `E-232__fan_1`, `E-232__fan_2`, `E-233__fan_1`, `E-233__fan_2`,
`FL-601__tip`) are in the optimised glb with the default `--instance true`: the optimiser did not
instance or drop them (their materials carry different AO images, and `extensionsUsed` is only
`EXT_meshopt_compression`, `EXT_texture_webp`, `KHR_mesh_quantization`). So `--instance false` was
not added. `check_glb.py` now requires these seven names (`separate_node_names`), pinned by
`tests/test_check_glb.py::test_separate_nodes_are_required`.

|---|---|---|---|---|

Cycles on the CPU, 128 samples on `high`, 34 baked groups (24 equipment roots, 7 separate nodes,
`SITE__ground`, `SITE__racks`, `SITE__fence`); the 15 piping routes are not baked. The 3 min 8 s run
was done while other work loaded the machine, which is why it was slower than the first; no claim
is made about the load during the final run.

## Fence extent fix (review finding)

The first post list ran along x to 201 (`round(200 / 3) + 1` posts), so two stray posts stood at
(201, 0) and (201, 150), 1 m outside the yard, while the rails ended at x 200. The post maths is now
the pure `scripts/blender/fence_math.py::fence_post_xy` (multiples of 3 m below the side length plus
the end point, no duplicate at a corner). The two tests in
`tests/blender/test_site_and_bake.py` were written first and seen red against the old maths
(`assert 235 == 233`: the two stray posts), then green. The glb was regenerated by
`scripts/build_station.sh high`: 233 posts (was 235), `SITE__fence` 6,804 triangles (was 6,860, 28
per post), and the `SITE__fence` POSITION accessor in the raw glb now spans x -0.03 to 200.03 (post
radius 0.03; it was 201.03 before; y of the glTF file is up, z is minus north: z -150.03 to 0.03).
Budgets after the fix are in the table above; the 168 draw calls, the 70 named nodes, the seven
separate nodes and 51 textures at 71.4 MB are unchanged. The review screenshot was **not** re-taken:
the review camera (spec `[45, 40, 25]` looking at `[80, 95, 3]`) does not see the east fence corners,
so the picture is unchanged by this fix.

## Ground (owner ruling C2)

Chosen: gravel diffuse multiplier **0.45** (`materials.GRAVEL_FACTOR`, applied to the yard `gravel`
and the outer terrain `gravel_far`; inside the ruled band 0.4 to 0.7). The sun intensity (2.5) and
`environmentIntensity` (0.8) in the frontend are unchanged here: both are inside the ruled bands
(1.5 to 2.5 and 0.4 to 0.8, at their upper edges) and the lights belong to Task 8, which may lower
them. A different HDRI or a new asset was not tried.

- Before: `2026-11-ks07-ground-before.png`, diffuse multiplier 1.0, `--bake low`, same camera and
  lights: the yard reads as snow (near white).
- After: `2026-11-ks07-review.png`, multiplier 0.45, `--bake high`, the final glb: a mid grey yard.
  A 0.4 build (`--bake low`) and the first 0.55 build were also looked at; 0.45 was picked between
  them and only the final build was kept as evidence.

## AO unwrap (owner ruling C3)

`bake.py` uses `bpy.ops.uv.smart_project(angle_limit=radians(66), island_margin=0.02,
scale_to_bounds=True)`; the parameter names were read from the 4.5.16 operator properties
(`angle_limit`, `margin_method`, `rotate_method`, `island_margin`, `area_weight`, `correct_aspect`,
`scale_to_bounds`), none was missing. Close-up before and after (K-202, V-212 and E-232 only,
`--only V-212,K-202,E-232 --bake high`, 512 px WebP, temporary close camera at spec
`[64, 63, 6]` looking at `[76, 75, 2]`, field of view 50 degrees; the camera file was restored):

- Before (`uv.lightmap_pack`): `2026-11-ks07-ao-before-lightmap.png`, 52.2 s bake.
- After (`uv.smart_project`): `2026-11-ks07-ao-after-smart.png`, 34.7 s bake.

The difference is visible but modest at this size: the lightmap version has grainy cells on the
ground and the skid deck, the smart-project version is smoother. These are my screenshot readings,
not a measurement.
