### SEC-1 (accepted at Gate 4): high advisory GHSA-fc5q-39xc-vjpf, no upstream fix

Status after the Gate 4 decision (2026-11-17, delegated owner decision in `docs/superpowers/plans/STATUS.md`,
entry "GATE 4 (delegated Opus)"): **accepted** in `docs/reference/SECURITY.md`, section "Accepted risks",
with a reason and a revisit date (Phase 6 Task 6 or 2026-12-15). The text below is the finding as it
was written before the decision.

- **What:** picomatch "ReDoS through single-branch repeated extglobs", CWE-1333, CVSS 7.5
  (`AV:N/AC:L/PR:N/UI:N/S:U/C:N/I:N/A:H`), affected `<=4.0.7`. `npm view picomatch` reports 4.0.7 as the
  latest version, so no patched release exists. npm's suggested `audit fix --force` (not run) would install
  vitest 3.1.4, vite 6.2.7 and other breaking downgrades; picomatch itself would stay at an affected
  version, so it is not a fix.
- **Where:** `picomatch@4.0.7` via `tinyglobby@0.2.17` and `fdir@6.5.0` (used by `json-schema-to-typescript`,
  `vite@8.3.8`, `vitest@5.1.0`, `@vitest/coverage-v8`, `typescript-eslint`). Nine packages show as high
  (`picomatch`, `fdir`, `tinyglobby`, `vite`, `vitest`, `@vitest/coverage-v8`, `@vitejs/plugin-react`,
  `json-schema-to-typescript`, `@typescript-eslint/typescript-estree`).
- **Exposure:** development tools only. `npm audit --omit=dev` finds 0, `npm ls picomatch --omit=dev` lists
  nothing, and the string `picomatch` is not in `app/frontend/dist`. The tools run on the owner's machine on
  repo-owned glob patterns; a ReDoS needs an attacker-controlled pattern or path, which this repo does not
  feed them. This is an assessment, not a test.
- **Why it blocked:** security-checks rule 10: a high finding blocks the phase until it is fixed or the owner
  accepts it in writing in `docs/reference/SECURITY.md` with a reason and a revisit date. I did not accept it
  and did not suppress it. `docs/engineering/coverage.json` entry B33 was `Blocked` for this reason; it is
  `Planned` since the acceptance (Gate 4 fix round).
- **Why it is new:** Task 11 recorded `npm audit --audit-level=high` exit 0 (9 moderate) earlier on
  2026-11-17; the advisory appeared in the database after that. The lockfile did not change
  (`git diff HEAD -- app/frontend/package-lock.json` is empty).
- **Options that were offered:** (a) accept in writing in `SECURITY.md` with a revisit date, for example the
  Phase 6 supply-chain task, and re-run the audit then (recommended: no fix exists and the exposure is
  development-only); (b) wait for a patched picomatch and update the lockfile; (c) an npm `overrides` entry
  to a fixed fork or version: none exists today, so not possible now.
